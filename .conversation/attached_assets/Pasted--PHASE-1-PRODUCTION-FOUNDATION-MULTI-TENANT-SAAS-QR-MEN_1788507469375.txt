# PHASE 1 — PRODUCTION FOUNDATION, MULTI-TENANT SAAS & QR MENU

## Goal

Build the production foundation of a multi-tenant QR restaurant ordering SaaS.

The system will support multiple restaurants from ONE Firebase project.

Each restaurant must have its own isolated data, dashboard, menu, tables, QR codes, staff accounts and settings.

Do NOT build ordering/payment/kitchen functionality yet. Phase 1 focuses on the production foundation, authentication, restaurant management, menu CMS, table management and customer-facing QR menu.

---

# 1. TECH STACK

Use:

* Next.js latest stable
* App Router
* TypeScript
* Tailwind CSS
* Firebase Authentication
* Firebase Realtime Database
* Firebase Storage
* Firebase Security Rules
* Firebase Admin SDK where server-side privileged operations are required
* QR generation library
* PWA-ready architecture
* Server-side validation
* Environment variables for secrets

Use clean modular architecture.

Do not put everything into one giant component.

---

# 2. MULTI-TENANT ARCHITECTURE

There will be ONE Firebase project.

Multiple restaurants live inside the same Firebase project.

Every restaurant has a unique immutable `restaurantId`.

Example:

restaurantId:
`rest_8F72KQ`

Restaurant:

```text
restaurants/
  rest_8F72KQ/
    profile/
    settings/
    categories/
    menuItems/
    tables/
    users/
```

Never trust a restaurantId supplied by the browser.

The authenticated user's restaurant membership must determine which restaurant they can access.

Every restaurant-specific database read/write must be authorized by Firebase Security Rules.

A user from Restaurant A must NEVER be able to access Restaurant B's data.

---

# 3. URL ARCHITECTURE

The public website uses:

```text
/
```

Restaurant customer menu:

```text
/menu/{restaurantSlug}/table/{tableSlug}
```

Example:

```text
/menu/cafe-mocha/table/table-04
```

Restaurant admin must use the restaurant-specific URL:

```text
/{restaurantSlug}/admin
```

Example:

```text
/cafe-mocha/admin
```

Login:

```text
/login
```

Platform owner/admin:

```text
/admin
```

The platform `/admin` is NOT the restaurant admin.

Restaurant dashboard must always know which restaurant it belongs to.

---

# 4. RESTAURANT SLUG SECURITY

Restaurant slug is only for routing and discovery.

Never use slug as a security mechanism.

Example:

```text
/cafe-mocha/admin
```

must NOT mean anyone can access Cafe Mocha's dashboard.

The user must:

1. Authenticate
2. Have an active account
3. Have membership in that restaurant
4. Have an appropriate role

If the authenticated user does not belong to the restaurant:

Return:

```text
403 Forbidden
```

Do not reveal restaurant information.

# 5. USER ROLES

Implement:

### Platform Admin

Can manage the entire SaaS platform.

### Restaurant Owner

Can manage their restaurant.

### Restaurant Manager

Can manage operational restaurant data according to permissions.

### Restaurant Staff

Limited operational access.

Create a proper role/permission system.

Never rely only on frontend hiding.

Backend/Firebase rules must enforce permissions.

# 6. AUTHENTICATION

Use Firebase Authentication.

Support:

* Email/password login
* Secure logout
* Password reset
* Session persistence
* Protected routes
* Authentication state handling

Never store passwords in Realtime Database.

Never store passwords in restaurant documents.

Never expose Firebase Admin credentials to the browser.

Use environment variables for server-side credentials.

---

# 7. RESTAURANT ADMIN ROUTE PROTECTION

When visiting:

```text
/cafe-mocha/admin
```

perform:

1. Check authentication.
2. Resolve restaurant by slug.
3. Determine user's restaurant membership.
4. Verify role.
5. Verify restaurant is active.
6. Only then render dashboard.

If not authenticated:

Redirect to:

```text
/login
```

If authenticated but unauthorized:

Show a clean 403 page.

Never render sensitive restaurant data before authorization.

# 8. DATABASE STRUCTURE

Use a clean structure similar to:

```text
restaurants/
  {restaurantId}/
    profile/
      name
      slug
      logoUrl
      phone
      email
      address
      city
      timezone
      currency
      createdAt
      updatedAt

    settings/
      orderingEnabled
      menuEnabled
      restaurantStatus

    categories/
      {categoryId}/
        name
        description
        imageUrl
        displayOrder
        active

    menuItems/
      {itemId}/
        categoryId
        name
        description
        price
        imageUrl
        veg
        popular
        available
        displayOrder
        createdAt
        updatedAt

    tables/
      {tableId}/
        tableNumber
        slug
        active
        pinHash
        createdAt
        updatedAt

    members/
      {uid}/
        role
        active
        createdAt

users/
  {uid}/
    name
    email
    restaurants/
      {restaurantId}/
        role
        active

restaurantSlugs/
  {slug}/
    restaurantId
    active
```

Keep IDs immutable.

Do not use restaurant names as database IDs.

# 11. IMAGE STORAGE

Food images must be stored in Firebase Storage.

Do NOT store image binaries inside Realtime Database.

Validate uploads:

* File type
* File size
* Image dimensions where practical

Only authorized restaurant users can upload/delete restaurant assets.

Prevent one restaurant from accessing another restaurant's Storage paths.

---

# 12. TABLE MANAGEMENT

Restaurant admin can:

* Create tables
* Rename table
* Activate/deactivate table
* Generate QR
* Regenerate table PIN
* Download QR
* Print QR
* View table status

Example:

```text
Table 01
Table 02
Table 03
Table 04
```

Each table receives:

* Unique table ID
* Table number
* Public table slug
* Random table PIN

The QR URL should look like:

```text
https://yourdomain.com/menu/cafe-mocha/table/table-04
```

The QR must NOT contain:

* Firebase credentials
* Admin information
* Passwords
* Secret keys
* Sensitive data

---

# 13. TABLE PIN SECURITY

QR codes are not secrets.

Anyone can photograph/share a QR.

Therefore create a table PIN system.

Example:

```text
Table 04
PIN: 7392
```

Do not store the raw PIN.

Store a secure hash.

PIN should be regeneratable without changing the QR URL.

Customer ordering security will be completed in Phase 2/3.

For Phase 1, implement the foundation needed for PIN validation.

# 17. FIREBASE SECURITY RULES

Write real production Firebase Security Rules.

Rules must enforce:

### Customer

Can only read public active menu information.

Cannot:

* Modify menu
* Modify prices
* Modify restaurant settings
* Modify tables
* Read private staff data
* Read owner data

### Restaurant Owner

Can only access their own restaurant.

### Restaurant Manager

Only permitted operations.

### Restaurant Staff

Only permitted operational data.

### Platform Admin

Platform-level access.

Never use:

```text
".read": true
".write": true
```

for production restaurant data.

Do not use frontend checks as the only security layer.

---

# 18. PRICE SECURITY FOUNDATION

The browser must NEVER be trusted for pricing.

The customer UI can display:

```text
₹180
```

but the server/database is the source of truth.

When ordering is implemented in Phase 2:

* Server retrieves current item price
* Server validates availability
* Server calculates total
* Client-submitted price is ignored

Prepare architecture for this now.

# 25. PHASE 1 ACCEPTANCE TEST

Before considering Phase 1 complete, verify:

### Multi-tenancy

* Restaurant A cannot access Restaurant B.
* Restaurant A owner cannot modify Restaurant B.
* Restaurant A cannot read Restaurant B private data.

### URLs

```text
/cafe-a/admin
/cafe-b/admin
```

work independently.

### Menu

Changing price updates customer menu.

Changing availability hides/disables item.

Adding an item appears without changing QR.

### QR

QR correctly opens:

```text
/menu/{restaurantSlug}/table/{tableSlug}
```

### Security

Unauthenticated user cannot access admin.

Restaurant user cannot access `/admin`.

Client cannot modify restaurantId to access another restaurant.

Storage isolation works.

### Production

No secrets exposed in browser.

No passwords stored in database.

No unrestricted Firebase rules.

No fake production data.
